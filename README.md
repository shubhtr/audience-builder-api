# Audience Builder — API

Chat-based audience builder for advertising campaigns. Media planners describe a target audience in plain English; the AI agent maps it to structured targeting signals drawn from real taxonomy data, lets the planner refine the signals conversationally, and estimates the reachable audience size on confirmation.

---

## Tech Stack

| Layer | Choice |
|---|---|
| Runtime | Node.js 20 + TypeScript (ESM, tsx) |
| Framework | Express 5 |
| Database | PostgreSQL (Supabase) via Prisma 7 |
| Auth | JWT (jsonwebtoken) + bcrypt |
| LLM | OpenRouter (configurable model, defaults to `openai/gpt-oss-120b:free`) |
| Taxonomy | CSV files loaded at startup, keyword-matched at request time |

---

## Setup

### Prerequisites

- Node.js 20+
- A PostgreSQL database (Supabase free tier works)
- An [OpenRouter](https://openrouter.ai) API key

### 1. Install dependencies

```bash
npm install
```

### 2. Configure environment

Copy `.env` and fill in your values:

```env
DATABASE_URL="postgresql://user:password@host:5432/dbname"

LLM_PROVIDER="openrouter"           # or "ollama" for local inference
OPENROUTER_API_KEY="sk-or-..."
LLM_MODEL_OPENROUTER="openai/gpt-oss-120b:free"

# For local inference (optional)
OLLAMA_BASE_URL="http://localhost:11434/v1"
LLM_MODEL_OLLAMA="qwen2.5:0.5B"

JWT_SECRET="change-this-in-production"
```

### 3. Run migrations and generate Prisma client

```bash
npx prisma migrate deploy
npx prisma generate
```

### 4. Start the server

```bash
npm run dev        # development (tsx watch)
```

Server runs on `http://localhost:3001`.

## API Reference

### Auth

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/api/auth/register` | `{ email, password, role? }` | `{ token, user }` |
| POST | `/api/auth/login` | `{ email, password }` | `{ token, user }` |

`role` must be `"ADMIN"` or `"PLANNER"` (defaults to `"PLANNER"`).

### Chat

| Method | Path | Auth | Body |
|---|---|---|---|
| POST | `/api/chat` | Bearer JWT | `{ message, conversationId }` |

Requires a valid JWT. The `conversationId` is a UUID generated by the client; the server creates the conversation on first use.

## Design Decisions

### Taxonomy as CSV files, not a database table

The four taxonomy sheets (location, transaction, consumer graph fields, consumer graph values) are loaded from CSV files at server startup into in-memory arrays. On each chat request, a keyword search runs against those arrays and injects the matching entries directly into the LLM prompt.

The alternative — seeding into database tables and querying with SQL — adds schema complexity with no practical benefit here: the full dataset is small (~750 entries total), never changes at runtime, and keyword search over an in-memory array is faster than a round-trip query. If the taxonomy grew or needed per-request filtering by category, a database table would be the right move.

### Multi-turn conversation passed as LLM message history

Rather than summarising previous turns or storing a "current signals" field on the conversation, the full message history is retrieved from the database and forwarded to the LLM as a standard `system / user / assistant` thread on every request. This means the model has complete context to understand what was previously proposed and what the user is asking to change, without any separate state-tracking logic on the server.

The trade-off is slightly higher token usage per turn. For conversations up to 20 messages (the current cap) this is negligible with any modern model.

### PROPOSE / REFINE / CONFIRM state machine in the LLM

The LLM is instructed to tag every response with one of three actions:

- **PROPOSE** — first signal recommendation
- **REFINE** — updated signals after user feedback ("remove golf", "add more premium signals")
- **CONFIRM** — final agreed set, triggered when the user approves

The server uses this tag to decide when to persist `confirmedSignals` on the conversation and when to calculate the reach estimate. The frontend uses it to decide which UI elements to render (the "Approve Signals" button, the confirmed banner, the reach estimate card).

Keeping the state machine inside the LLM rather than in server code means it handles natural language approval gracefully ("looks good", "yes exactly", "ship it") without a list of keyword matches.

### Reach estimation formula

No real audience count data is provided, so reach is estimated with a deterministic formula:

```
reach = max(10_000, 5_000_000 − (signalCount × 300_000))
```

More signals = narrower audience. The floor of 10,000 prevents the estimate from going to zero for highly targeted audiences. The estimate is only surfaced after the user confirms signals — before that it would be misleading to show a number for an audience that is still being defined.

### Role-based permissions

Two roles: `ADMIN` and `PLANNER`. Both can use the chat. Admins additionally receive a `debug` field in the chat response containing the model name used. The role is encoded in the JWT at login and verified by the `authorize` middleware on protected routes without a database round-trip.

### Conversation persistence and resumption

Conversations are stored in PostgreSQL. Each `Message` row holds a `content: JSONB` column containing the full structured payload (text, signals, action, reach estimate). The client generates a UUID for the conversation and passes it on every request; the server upserts the conversation on first use. To resume a conversation, the client just uses the same UUID — the history is reloaded from the database on each turn.

Currently the client stores the active conversation ID in `localStorage`. A full implementation would expose a `GET /api/conversations` endpoint so users can list and switch between past conversations.
